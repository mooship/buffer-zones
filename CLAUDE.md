# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Stratum is a reusable SDK for building public-interest geospatial layer platforms: a domain-agnostic layer model, generic map rendering, and React hooks (`@stratum/core`, `@stratum/map`, `@stratum/react`) that any dataset can be wired into. `packages/app` and `packages/web` are the SDK's reference implementation, not the product — a real, published SSR app on Cloudflare Workers (no accounts, no tracking beyond cookieless page views) that proves the SDK out end-to-end. That implementation's one domain, `gauteng-spatial-legacy`, maps apartheid-era spatial planning legacy across South African metros using one combined regional map layer: recognized township areas, formal transit routes, and modeled car drive-time to selected job centers. That domain's data currently covers the `gauteng` region: all nine Gauteng municipalities, including Tshwane/Pretoria and Johannesburg.

## Commands

```bash
npm install
npm run test        # vitest across the npm workspaces under packages/*, plus data-pipeline (see vitest.config.ts projects)
npm run test:coverage # vitest run --coverage, same scope
npm run typecheck   # tsc --noEmit for @stratum/core, @stratum/app, @stratum/map, @stratum/react + web build + data-pipeline typecheck
npm run build       # build all workspaces
npm run lint         # biome check .
npm run format       # biome format --write .
npm run dev --workspace @stratum/web
```

Run a single test file: `npx vitest run path/to/file.test.ts` (or `npx vitest path/to/file.test.ts` to watch).

Playwright end-to-end tests live in `packages/web/e2e/`. They are not part of `npm run test`, and run in CI via a dedicated GitHub Actions workflow (`.github/workflows/playwright.yml`):

```bash
npm run playwright:install --workspace @stratum/web  # once, downloads the Chromium binary
npm run test:e2e                                     # builds packages/web and runs the suite against the production preview server
npm run test:e2e:ui --workspace @stratum/web          # Playwright's interactive UI runner
```

`data-pipeline/` is **not** an npm workspace — it's a standalone project with its own `package-lock.json`, but its vitest suite is still included as a project in the root `vitest.config.ts`, so `npm run test` and CI's `test` step run it too:

```bash
cd data-pipeline
npm install
npm run run       # full pipeline: fetch boundaries/transit, OSRM routing, join, write output
npm run display   # legacy helper: rebuilds compact display files for per-metro source directories when present
```

Pre-commit (lefthook) runs biome (auto-fix staged files) and the full vitest suite — expect both to run on every commit.

## Architecture

**Three parts, one direction of data flow:** `data-pipeline` (offline, run manually) → static GeoJSON committed per-region under `packages/web/public/data/<regionId>/` → `packages/web` (client-side fetch for map data; the one runtime API route, `/api/ask`, exists only to proxy Workers AI, not to serve map data). `packages/app` is the contract both ends agree on, built on top of the domain-agnostic model in `packages/core`.

- **packages/core** — domain-agnostic layer model (`Layer`, `LayerGroup`, style config types, in `types/layer.ts`), a Leaflet config factory (`createLayerConfig`, converting a `Layer` into Leaflet `pathOptions`/`styleFn`), a registry factory (`createRegistry`, exposing `getLayers`/`getLayer`/`getLayerGroups` over a `DomainConfig`), an LLM-prompt serializer (`describeDomainForPrompt(domain)`, turning a domain's available layers/layer groups into a compact plain-text block — labels, geometry kind, descriptions, group membership — deliberately excluding `dataSource`/`style`/coordinates, for grounding an AI feature's system prompt without depending on any AI vendor), and geodata utils (`fetchFeatureCollection`, `mergeFeatureCollections`, and the Zod schemas in `geoJsonSchemas.ts` — `featureCollectionSchema`, `polygonGeometrySchema`, `multiPolygonGeometrySchema`, `createFeatureCollectionParser`). Every export is JSDoc-documented. Has no dependency on `packages/app`, `packages/web`, or React — it's the first package extracted towards a reusable SDK.

- **packages/app** (`@stratum/app`) — Gauteng-specific constants (metros, regions, townships, transit layer ids), domain data, and Gauteng-specific GeoJSON type definitions. `types/genericLayer.ts` still re-exports the `Layer`/`LayerGroup` contracts (style config, geometry kind, interaction, grouping/selection mode) from `@stratum/core`, which any domain's layers must satisfy, but `domains/gauteng-spatial-legacy/layers.ts` imports `Layer` directly from `@stratum/core` rather than through that stub. `domains/gauteng-spatial-legacy/` (`layers.ts`, `layerGroups.ts`, `index.ts` exporting `GAUTENG_SPATIAL_LEGACY_DOMAIN`) is the first concrete domain built on those types — it wires up the Gauteng layer catalogue, layer groups, and "why this map exists" story copy (the `rapid-rail` and `commuter-rail` layers set `hasPointGeometry: true`, since real station/stop Point geometry only exists for those two networks). `datasetSummary.ts`'s `buildGautengDatasetSummary()` derives a static, plain-text scale summary (metro/township-area/job-centre counts, transit networks covered) from `METROS`/`TOWNSHIP_AREA_DEFINITIONS`, exposed as `GAUTENG_SPATIAL_LEGACY_DOMAIN.datasetSummary` — grounding context for `packages/web`'s Ask AI feature, deliberately reporting counts rather than per-feature figures since the underlying GeoJSON is megabytes of coordinate data, far past what fits in a prompt on Workers AI's free tier. `constants/regions.ts` defines `REGIONS` (currently one entry, `gauteng`, kind `province`), the registry driving per-region output directories and data-fetch URLs. `constants/metros.ts` still defines `METROS` (currently the nine Gauteng municipalities), each tagged with a `regionId`, used by the pipeline while building a region's dataset. `constants/townships.ts` defines included township-area groupings per metro. `types/` also holds Gauteng-specific GeoJSON/transit contracts. Renamed from `packages/shared`/`@stratum/shared`.

- **packages/map** — generic map rendering components (`MapView`, `Legend`, `DesktopLegend`, `MobileLegend`, `LocationSearchControl`, UI primitives `IconButton`/`SegmentedControl`/`ControlButton`/`ThemeToggle`/`BasemapToggle`/`SettingsMenu`), a `DomainProvider` React context plus `useDomain()` hook wrapping `createRegistry` from `@stratum/core`, and Leaflet-specific utilities (`constants/basemaps.ts`, `constants/mapStyles.ts`, `data/locationSearch.ts`). `DomainProvider` must wrap any component tree that calls `useDomain()` — directly (`Legend`, `MapView`) or transitively (`DesktopLegend`, `MobileLegend`); `useDomain()` throws if called outside one. `MapView` takes a domain-agnostic `bounds` prop (no baked-in Gauteng bounds), a `renderFeaturePopup` callback so popup content stays caller-defined rather than hardcoded to a Gauteng township shape, and an optional `onLayerDataError` callback fired with the ids of overlay layers whose data failed to fetch (from its internal `useLayerData` call), so a failed background fetch isn't silently invisible to the caller. `usePrefersDarkMode`/`useThemePreference` are imported directly from `@stratum/react` (no re-export stub). Built on `@stratum/core` and `@stratum/react`; still has no dependency on `packages/app` or `packages/web`, taking `DomainConfig`/`Layer` values as props/context instead.

- **packages/react** — generic React hooks with no map/domain dependency: `usePrefersDarkMode()` (tracks the OS `prefers-color-scheme: dark` media query), `useThemePreference()`/`setThemePreference()`/`initTheme(config)` (a `useSyncExternalStore`-backed theme preference store, persisted to `localStorage`, syncing `document.documentElement.dataset.theme` and a `<meta name="theme-color">` override), and `useAskAi()`/`askAi()`/`resetAskAi()`/`initAskAi(config)` (the same module-singleton-plus-`useSyncExternalStore` pattern, for a streaming Q&A conversation). `initTheme({ storageKey, colors })`/`initAskAi({ endpoint })` must each be called once at app bootstrap, before hydration, with app-specific values — neither the theme storage key/colour pair nor the Ask AI endpoint URL are baked into their hooks; calling `initTheme` also re-reads the already-stored preference under the new key, since the module's own top-level read (at import time, before `initTheme` can run) used the built-in default config. `useAskAi` is deliberately vendor-agnostic: `askAi()` `POST`s `{ message, history }` as JSON to the configured `endpoint` and streams back plain UTF-8 text (a non-200 response is read as JSON `{ error }` instead) — no Cloudflare/Workers AI-specific code lives here, so any backend speaking that tiny contract works ("bring your own AI"; see `packages/web`'s `/api/ask` for the one that does). The third package extracted towards a reusable SDK.

- **data-pipeline** — pipelines are described declaratively as a `RegionPipelineConfig` (`src/pipelineSource.ts`): a `regionId`, the `metros` it covers, and a list of `PipelineSource` entries (`layerId`, `fetch()`, `outputFileName`) each responsible for producing one transit layer's `FeatureCollection`. `src/regions/gautengPipelineConfig.ts` is the first such config, wiring up Gautrain rail/bus, PRASA rail, A Re Yeng, Rea Vaya, Ekurhuleni IRPTN, and Tshwane bus fetchers into `GAUTENG_PIPELINE_CONFIG`. `src/run.ts` runs `runRegion(config)` (looped across every configured region by `runAllProvinceRegions()`, or invoked for a single region via `npm run run -- --region gauteng`): loops through the config's `metros` to fetch boundaries and per-metro OSRM job-center routing, runs each `PipelineSource.fetch()`, computes nearest-transit distance, then writes that region's combined dataset under `packages/web/public/data/<regionId>/` (including `townships`, `township-areas`, and one file per configured transit source, plus `.display.v1.geojson` variants). Only the `gauteng` region exists today.

- **packages/web** — `layers/registry.ts` wraps `createRegistry` from `@stratum/core` around `GAUTENG_SPATIAL_LEGACY_DOMAIN`; there is no metro argument or per-domain selector yet since only one domain is published. The re-export stubs that used to sit between web and the SDK packages have been removed: `App.tsx` and its components import `createLayerConfig`, `fetchFeatureCollection`, `mergeFeatureCollections`, `MapView`, `Legend`, `DesktopLegend`, `MobileLegend`, `LocationSearchControl`, the shared UI primitives, `getBasemapTileSources`, `usePrefersDarkMode`, and `useThemePreference`/`initTheme` directly from `@stratum/core`, `@stratum/map`, and `@stratum/react`; `useLayerData` similarly lives only in `@stratum/map`, not in web. `data/geoJsonSchemas.ts` re-exports the generic schemas from `@stratum/core` and adds the township-specific `townshipFeatureCollectionSchema`. `constants/themeConfig.ts` holds the app-specific `THEME_COLOR`/`THEME_STORAGE_KEY` values (the `buffer-zones-theme` storage key predates the Stratum rename and is kept as-is to avoid discarding users' stored preference); `entry.client.tsx` calls `initTheme({ storageKey: THEME_STORAGE_KEY, colors: THEME_COLOR })` and `initAskAi({ endpoint: ASK_AI_ENDPOINT })` before `hydrateRoot`, and `public/theme-bootstrap.js` (a static script, can't import the constant) duplicates the same literal storage key to set `data-theme` pre-hydration and avoid a flash of the wrong theme. `App.tsx` wraps its whole render tree in `<DomainProvider domain={GAUTENG_SPATIAL_LEGACY_DOMAIN}>` (both `MapView` and the always/conditionally-rendered `DesktopLegend`/`MobileLegend` need `useDomain()`), passes `MapView` a Gauteng `bounds` constant and a `renderFeaturePopup` that renders `TownshipPopup`, which stays web-local since popup content is domain-specific. Each layer's `dataSource` is a list of URLs built via `buildRegionDataUrls()` and pointing at `/data/<regionId>/*.geojson`, one per region in `REGIONS`. UI state in `stores/useMapUiStore.ts` contains layer visibility, basemap, panel state, and selection only; there is no metro or region selector state. `App.tsx` fetches every region's township/area data and merges the resulting `FeatureCollection`s client-side — that data still feeds the map's choropleth layers and `TownshipPopup` (rendered via `renderFeaturePopup` on every map feature click, unconditionally) even though there's no longer a "places" browsing UI for it; `MapView`'s internal `useLayerData` call does the same per-layer for transit overlays, reporting failures back to `App.tsx` via an `onLayerDataError` callback that `LayerToggles` surfaces as a per-layer badge. The info panel has two tabs only — `layers` (`LayerToggles`) and `ask`; there is no "story"/"the pattern" methodology tab or "places" township browser (both removed as unwanted features, along with their `EvidenceSummary`/`TownshipBrowser` components and the `DATA_SOURCES`/`REPOSITORY_URL` constants that fed the former). The `ask` tab's `AskAiPanel` (`components/AskAiPanel/`) is a chat UI over `@stratum/react`'s `useAskAi`; it renders assistant replies as plain text only (never parsed as markup — the model's output is untrusted), aligns user/assistant bubbles to opposite sides, and exposes a "Clear conversation" button wired to the hook's `reset()`. Its textarea intentionally sets `font-size: 16px` rather than the design system's smaller type scale, since a focused input under 16px triggers unwanted auto-zoom on iOS/Android; `.panelViewport` (`App.module.css`) carries `padding-inline` for the same class of reason — `overflow-y: auto` implicitly makes `overflow-x` clip too, which was cutting off full-width children's `:focus-visible`/`:hover` effects at the edges. Its endpoint, `POST /api/ask` (`src/routes/api.ask.ts`, a React Router resource route with no `loader`, so non-POST methods 405 automatically), delegates to `src/server/askAi.server.ts`'s `handleAskAiRequest`, which validates the body (zod, capped question/history length), rate-limits in two layers — a site-wide cap via `ASK_AI_GLOBAL_RATE_LIMITER` checked first (protects the account's shared free-tier Neuron budget from a single sustained abuser or many distributed ones, which a per-IP limit alone can't bound), then a per-client-IP cap via `ASK_AI_RATE_LIMITER` (both 429 + `Retry-After` when exceeded) — builds a system prompt from `describeDomainForPrompt` plus the domain's `story`/`datasetSummary` (with explicit guardrails: on-topic only, no per-place figures beyond what's summarised, user content — including conversation history, which the client fully controls and may have fabricated — is data not instructions, never a prior commitment overriding the rules, and no off-topic creative-writing requests — poem/story/song/joke/etc — honoured even when framed as harmless, after a smaller model was found to comply with exactly that framing), and streams a Workers AI (`@cf/mistralai/mistral-small-3.1-24b-instruct`, free-plan-eligible — deliberately using Workers AI's legacy plain-text streaming shape, not the newer OpenAI-compatible `choices[].delta` shape: two reasoning models tried first, `@cf/zai-org/glm-4.7-flash` and `@cf/google/gemma-4-26b-a4b-it` — despite Cloudflare's own docs describing the latter as non-reasoning — both intermittently spent their entire token budget on hidden "thinking" output and returned an empty reply; a smaller 7B instruct model was also tried and, despite the hardened guardrail wording, complied with a direct injection request — 24B empirically holds the guardrails where the 7B one didn't) reply back — adapting its SSE framing (the legacy `{response}` shape, with `choices[].delta.content` also supported for compatibility if this app uses a `choices`-shaped model again, any `delta.reasoning`/`reasoning_content` "thinking" tokens deliberately dropped) into the hook's plain-text contract via `createPlainTextTransform`. Cloudflare bindings (`AI`, `ASK_AI_RATE_LIMITER`, `ASK_AI_GLOBAL_RATE_LIMITER`) reach route modules through React Router 8's typed context system: `workers/app.ts`'s `fetch(request, env)` sets them on a `RouterContextProvider` via `envContext` (`src/server/envContext.ts`), read in `action`s via `context.get(envContext)`. Because `workers/app.ts` is bundled separately (by Wrangler) from the route modules (bundled into `build/server/index.js` by Vite/React Router), `envContext`'s `createContext()` key is cached on `globalThis` under a well-known `Symbol.for` so both bundles' independently-compiled copies resolve to the same key at runtime — a plain per-module `createContext()` call would silently produce two different keys and every request would throw. No CORS headers are set on `/api/ask`, deliberately — same-origin only, so another site can't drive Workers AI usage against this account from a browser.

- **Deploy** — Cloudflare Workers runs the wrapper entry (`packages/web/workers/app.ts`) which imports the built React Router server bundle (`packages/web/build/server/index.js`), and serves built client assets from `packages/web/build/client` (`wrangler.jsonc`). `wrangler.jsonc` also declares the `AI` binding (Workers AI, included on the Workers Free plan: 10,000 Neurons/day, no API key needed) and two Workers Rate Limiting bindings (GA, free-plan-compatible) backing the Ask AI feature: `ASK_AI_RATE_LIMITER` (per-client-IP) and `ASK_AI_GLOBAL_RATE_LIMITER` (site-wide, guarding the shared daily Neuron budget). Full/100 Lighthouse scores and mobile-friendliness are a hard requirement, not aspirational — this drives decisions like the `.display.v1.geojson` simplification step and self-hosted variable fonts.

- **Testing** — vitest unit/component tests (gated in CI) deliberately mock `react-leaflet`, so real Leaflet rendering, tile requests, and popup/tooltip binding are untested there by design. `packages/web/e2e/` fills that gap with Playwright, run on demand against a production SSR preview (`npm run build && npm run preview --workspace @stratum/web`) with basemap tile requests mocked to a 1x1 PNG so the suite doesn't depend on OSM/CARTO/Esri availability.

## Conventions

- **TDD.** Write the failing test before implementation code, for both bug fixes and new features.
- **JSDoc on every exported function, const, type, interface, class, and component** (TSDoc-compatible: `@param`, `@returns`, `@remarks`, `@example`) — across every package, not just the SDK ones (`@stratum/core`/`map`/`react`). Document the *why*/non-obvious behaviour, not just a restatement of the name; skip fields that are already self-evident from their name and type.
- **SOLID, DRY, KISS, YAGNI.** Prefer the simplest design that satisfies current requirements; don't build for hypothetical future needs.
- **No code comments** unless they capture a genuinely non-obvious *why* (a constraint, a workaround, an invariant) — never restate what the code already says.
- **Expanded `if` statements with braces**, never single-line/braceless conditionals. Biome's `useBlockStatements: error` rule enforces this — don't disable it.
- **Accessibility is a priority**, not an afterthought — semantic HTML, keyboard navigation, focus states, and contrast should be considered in every UI change, in step with the Lighthouse-100 bar above.
- **British English spelling and grammar** in all user-facing copy (UI text, labels, error messages) — not in code identifiers.
- Prioritise **superpowers** skills for their intended workflows (brainstorming before creative/design work, TDD, systematic debugging, etc.) rather than working ad hoc.

## Design system

Named CSS custom-property colour tokens (`--color-ink/panel/line/paper/ochre/redearth/muted/surface`, defined in `packages/web/src/index.css` with separate light/dark-mode values), Inter Variable and Martian Mono Variable as the two self-hosted variable fonts, and a recurring hairline-border-plus-shadow-elevation motif rather than translucent "glass" materials. Structural chrome (the info panel, bottom sheet, settings menu, legend, popups, controls) is an opaque, tonal `--color-surface-container`/`--color-surface-container-high` colour — a small tint of `--color-primary` mixed into `--color-panel`, both derived once in `index.css` so they adapt across themes automatically — differentiated by a `--shape-*` corner radius and an `--elevation-1/2/3` shadow tier, never by `backdrop-filter`/blur. Hover/pressed/selected states use the `--state-hover`/`--state-pressed`/`--state-selected` opacity-tint tokens rather than each component picking its own translucency percentage. Token and class names describe what a value is (a surface tier, an elevation, a shape, a state layer), deliberately avoiding names tied to any one vendor's design language. See `docs/design-system.md` for the full token reference. Keep new UI consistent with this rather than introducing new ad hoc styles or fonts.
